Teamsアレルギーをなくそう

Google Workspaceで働く我々が、Microsoftを使う先方の環境で迷わないための対応表

対象: 社内でGoogle Workspace・Slack・Notionを使い、先方はMicrosoft 365が多い会社のメンバー 時点: 2026年11月。名称と価格は頻繁に改定されるため、提案に使う前に公式情報で確認する
Teams Outlook Copilot Copilotエージェント Power Automate Power BI Azure AI Search Blob Storage Document Intelligence Entra ID

0. 全体地図：Microsoftは3階建て＋土台

要点（3つ）
  1. 3つの階が1つのアカウント基盤（Entra ID）の上にある。これがMicrosoftの強さであり、先方の情報システム部門がMicrosoftで統一する理由である
  2. 「テナント」は会社ごとに1つ作成されるMicrosoftの契約単位である。先方のTeamsに参加する時、我々は先方のテナントにゲストとして入る
  3. Copilotは3階、Copilot Studioは2階、Azure OpenAIは1階にある。同じ「AI」でも階が異なれば、使う人も契約も異なる

1. Teams：Slack＋Google Meet＋共有ドライブを1つにしたもの

1-1. 構造

Slackとの対応表
TeamsSlack注意点

チーム該当なし（チャンネルの束）チームに入らないとチャネルが表示されない
チャネルチャンネル標準・プライベート・共有の3種

1-2. 我々がTeamsで迷う3つの理由

  1. テナントの切り替え: 我々は自社テナントを持たず、先方ごとにゲストとして参加する。先方が3社あれば3つのテナントを右上のアカウント表示から切り替える。表示中ではないテナントの通知は遅れることがある
  2. チャットとチャネルの区別: 重要な連絡がチャネルに投稿され、我々がチャットだけを確認していると見落とす。先方の宿題や経緯はチャネルのスレッドに残ることが多い
  3. ファイルの保存先が見えない: Teamsで共有されたExcelの実体はSharePointにある
注意
ゲストはダウンロードを制限されている場合があり、これは先方の管理者の設定である（我々の操作ミスではない）

1-3. 実務の作法（5つ）

実務
  • Teamsはブラウザ版でなくデスクトップアプリで使う。複数テナントの通知を受け取りやすい
  • 先方への連絡は、該当スレッドへの返信で行う。新規投稿は話題を変える時だけにする
  • @メンションは個人宛てに付ける。チャネル全体へのメンションは先方の全員に通知されるため避ける
  • 我々はTeams会議を自分で発行できない（Microsoft 365の有料ライセンスが無いため）。先方にTeams会議のURLを発行してもらうか、こちらからGoogle Meetを送る。先方の社内規程でMeetに接続できない会社もある
  • 会議の録画と文字起こしは開催者（先方）のOneDriveに保存される。我々が後から閲覧できるかは先方の共有設定で決まる

2. Copilotとは何か：対比から輪郭を定める

2-1. 「Copilot」は6つの製品の総称である

Microsoft Copilot一般消費者向けのAIチャット個人無料（有料版あり）

2-2. ChatGPT・Claude・Geminiとの対比

  1. 社員が質問を入力する
  2. Copilotが Microsoft Graph（メール・予定・Teams・SharePoint・OneDriveの索引）を検索する。検索範囲はその社員が閲覧権限を持つものだけ
  3. 検索結果と質問を合わせて、大規模言語モデル（主にOpenAIのGPT系。2025年以降はAnthropicのClaudeも一部機能で選択できる）に送る
  4. 回答に出典のファイル・メールへのリンクを付けて返す
  5. データはMicrosoft 365の契約範囲内で処理され、モデルの学習には使われない
対比表
観点M365 CopilotChatGPT Enterprise / Claude for WorkGemini（Google Workspace）
頭脳＝言語モデルGPT系が中心、Claudeも一部自社モデルGemini
社内データへの接続Microsoft Graphに標準で接続コネクタを個別に設定Google ドライブ・Gmailに標準で接続

So What
Copilotの価値は言語モデルの性能ではなく、社内データへの接続と権限の継承にある。言語モデルの性能だけを比較すればChatGPTやClaudeが上回る場面は多い。先方が「Copilotは賢くない」と言う時は、多くの場合モデルの問題ではなく、根拠にする社内データが整理されていないことが原因である。

2-3. 導入時に必ず起きる問題：過剰共有

注意
Copilotは閲覧権限のあるファイルをすべて検索対象にする。「全社員に共有」のまま放置された人事資料や給与表があれば、Copilotはそれを回答の根拠に使う。人間は存在を知らないファイルを開かないが、Copilotは検索で見つける。このため、先方の情報システム部門はCopilotの導入前にSharePointの共有設定を点検し、公開範囲の広すぎる設定を是正する。導入支援の提案では、この点検と是正を最初の工程に置く。

3. Power Automate・Copilotエージェント・Copilot Chat・Power BI：4つの役割

3-1. 一言で言うと

  • Copilot Chat = 人が質問して答えを受け取る場所。毎回人が指示する
  • Copilotエージェント = 特定業務向けに設定したCopilot。指示文・参照資料・実行できる操作を事前に登録する。例：社内規程に答えるエージェント、問い合わせを一次対応するエージェント
  • Power Automate = 決まった手順を自動で実行する仕組み。「メールが届いたら添付をSharePointに保存してTeamsに通知する」のように、きっかけ（トリガー）と操作（アクション）を並べる。判断はしない
  • Power BI = 数字を集計して見せるダッシュボード。ExcelやデータベースからデータをGoogleのLooker Studioと同様に可視化する

Power Automate

  • クラウドフロー（Web上のサービス同士をつなぐ）とデスクトップフロー（Windows画面の操作を記録して再生するRPA）の2種
  • 接続先（コネクタ）は1,000種類以上。標準コネクタはMicrosoft 365に含まれ、Salesforce等のプレミアムコネクタは追加ライセンスが必要

Copilotエージェントの作成方法は2つ

  • エージェントビルダー: Copilot Chatの画面上で、指示文と参照ファイルを登録するだけで作成できる。簡易版

Power BI

  • Exchange Online = メールと予定表のデータを保管するサーバー
  • 我々の対応: Gmail・Googleカレンダー（アプリとサーバーが一体）

5. Azure：Microsoftのクラウド基盤

5-1. 位置づけ

AWS・Google Cloudと同じ種類のクラウドである。サーバー・保存領域・データベース・AIの部品を、使った分だけ借りる。

大企業がAzureを選ぶ理由:

  1. 既にMicrosoft 365を契約しており、アカウント（Entra ID）と請求をまとめられる
  2. OpenAIのモデル（GPT系）を、自社の契約・日本国内のリージョンの中で使える（Azure OpenAI）。入力データはモデルの学習に使われない
  3. 包括契約（エンタープライズ契約）の中で調達でき、新規の取引先審査が不要になる

5-2. 階層構造

AWSとの対応: サブスクリプション≒AWSアカウント、リソースグループ≒タグでまとめた単位（AWSに完全な対応物はない）

6. Azure AI Search：社内文書を検索可能にする索引サービス

6-1. 何をするものか

大量の文書から、質問に関係する箇所を探し出すサービスである。生成AIに社内文書を根拠として回答させる仕組み（RAG：検索拡張生成）の「検索」部分を担う。旧名称はAzure Cognitive Search。

6-2. 4つの構成要素

  • インデックス: 検索用に整理したデータの表。本の巻末索引にあたる。「本文」「ファイル名」「更新日」「ベクトル」などの列を定義する
  • インデクサー: Blob Storage等のデータソースを定期的に確認し、新しい文書をインデックスに取り込む自動処理
  • スキルセット: 取り込みの途中で行う加工。文字の読み取り（OCR）、文書の分割（チャンク化）、ベクトル化（埋め込み）など
  • クエリ: 検索の実行。下記の3方式から選ぶ

6-3. 3つの検索方式

So What
キーワード検索とベクトル検索は互いの弱点を補う。業務文書には型番・条文番号・社内用語が多いため、ベクトル検索だけでは精度が出ない。標準はハイブリッド検索＋セマンティックランカーである。

6-4. 費用の考え方

注意
AI Searchは検索した回数ではなく、起動している時間に応じて課金される（料金区分×ユニット数×時間）。使っていない夜間も課金される。PoCでは最小の区分で開始し、文書量と同時アクセス数に応じて区分を上げる。

7. その他：Blob StorageとDocument Intelligence

7-1. Blob Storage：ファイルの保管庫

  • Azureのファイル保管サービス。AWSのS3、Google CloudのCloud Storageに相当する
  • 構造: ストレージアカウント ＞ コンテナー（フォルダに相当） ＞ Blob（個々のファイル）
  • アクセス頻度に応じて料金区分を選ぶ: ホット（頻繁に読み出す）／クール／コールド／アーカイブ（年に数回しか読み出さない。最も安価だが取り出しに時間がかかる）
  • SAS（共有アクセス署名）: 期限付きでファイルへのアクセスを許可するURL。外部への受け渡しに使う
  • RAGでは、PDFやWord等の元文書をここに保管し、AI Searchのインデクサーがここから取り込む

7-2. Document Intelligence：文書の構造を読み取るサービス

  • 旧名称はForm Recognizer。PDFや画像から、文字だけでなく表・見出し・段落・チェックボックスの位置関係まで読み取ってJSONで返す
  • 単純なOCRとの差: OCRは文字の並びを返すだけで、表の行と列の対応が失われる。Document Intelligenceは表を表として返す
  • 主なモデル:
    • Read: 文字の読み取りだけ
    • Layout: 表・見出し・段落の構造まで読み取る。Markdown形式でも出力できる。RAGの前処理で最もよく使う
    • 事前構築モデル: 請求書・領収書・身分証明書など、決まった書式の項目を読み取る
    • カスタムモデル: 自社の帳票を数件学習させて、必要な項目を読み取る
  • 日本語の縦書き・手書きにも対応するが、精度は文書の品質で大きく変わる。PoCで実物の文書を数十件通して確認する
