Docker, Inc.

非上場 Y Combinator S10（前身 dotCloud） 事例研究 本レポート作成日：2026年7月27日／作成視点：スタートアップ事例研究（売り先ではなく学習対象）

技術は業界標準になり、会社は事業を切り売りして小さくなった。Docker は買収されて消えたのでもなく、順調に伸び続けたのでもない。2019年11月に主力の Docker Enterprise 事業を Mirantis へ売却し、従業員を約400名から60名へ絞り、CEO を交代させて開発者向け専業として作り直した企業である。本レポートは、捨てるはずだった社内ツールが本体を超えた2013年の転換と、標準を取ったのに収益化できず事業を手放した2019年の転換を、同じ会社の同じ構造から生じた表裏として扱う。

この事例の核心：Docker は技術的成功と事業的成功が分離した典型例である。コンテナは2026年時点でソフトウェア配布の事実上の標準になり、その仕様の中核である runC は Open Container Initiative に7、ランタイムの containerd は Cloud Native Computing Foundation に8、いずれも Docker 自身が寄贈した。標準化の主導者でありながら、Docker, Inc. の評価額は2015年の約10億ドル10から2022年でも21億ドル19,20と、7年で2.1倍にとどまっている。同じ7年間で、この技術の上に立つ Kubernetes エコシステムは業界のインフラ層をまるごと置き換えた。標準を作ることと、標準から徴収することは別の能力であるという論点が、この会社の全期間を貫いている。

②創業ストーリーと初期プロダクトOrigin — 捨てるはずだったものが本体になった

初期プロダクト：dotCloud は PaaS だった

dotCloud は Y Combinator Summer 2010 バッチに参加した、Platform as a Service（PaaS）のスタートアップである1。開発者がコードを push すれば実行環境が用意される、当時の Heroku と同じ市場を狙う製品だった。差別化はその実装にあり、dotCloud は内部で Linux コンテナを使って複数の言語スタックやデータベースを同一基盤に載せていた。コンテナは当初、外向きの製品ではなく自社PaaSを安く回すための内製の道具だった。

Hykes は後年、PaaS 市場そのものの構造的な難点として、業界全体がベンチャー資金で補助された AWS への送客装置になっていた点を挙げている。顧客が成長すると専任のDevOps担当を雇い、同じものを自前で AWS 上に構築してしまうため、伸びた顧客ほど離脱する11。後述する Ben Golub の、最良の顧客ほど自社を卒業してしまうという発言3と同じ現象を指している。

ピボットの引き金：失敗ではなく「速さの不足」

Solomon Hykes は後年、dotCloud は失敗していなかったと明言している。有料顧客があり、銀行口座には十分な資金があった。彼の表現では、ゆっくり茹でられる蛙の状況、つまり毎月前進はしているが十分な速さではない、というものだった1。

Hykes の説明（要旨）：dotCloud は決して失敗ではなかったが、成功するのが十分に速くなかった。Docker は問題を解こうとした6回目の試みであり、前の5回が失敗したのは、dotCloud を続けながら片手間で新しいことをやろうとしたからである。15人の会社でその戦略は成立しない1。

2013年初頭に Hykes は転換を決め、取締役会がこれを後押しした。転換にはエンジニアへ既存の仕事の破棄を告げ、人員を削減する工程が伴っている1。どうせ失敗するなら自分たちが興奮できるもので失敗しようという言い方で、片手間の並行を止めて全面移行した点が、6回目だけが成功した理由として語られている1。

公開：2013年3月15日、PyCon の5分間

Docker が公に姿を現したのは、2013年3月15日、PyCon US 2013 のライトニングトークである。Solomon Hykes が「The future of Linux Containers」と題した5分間の枠で、dotCloud が内部で使っている Linux コンテナ技術を、誰でも使える形にまとめたものとして Docker を実演した2。同年3月に Apache 2.0 ライセンスの OSS として公開されると、想定を超える速度で採用が広がった1。

Docker の発明は何だったのか（ここを曖昧にしない）：コンテナを構成する要素技術は Docker の発明ではない。プロセス隔離の LXC、リソース制御の cgroups、名前空間の namespaces はいずれも Linux カーネル側に既に存在していた。Docker が作ったのはそれらを開発者が1行のコマンドで使える形にまとめ、イメージという配布可能な単位と、それを置く公開レジストリを与えたことである。発明の対象はカーネル機能ではなく、パッケージング、配布形式、そして開発者の手数だった。この価値の置き方が後の収益化の困難に直結する。使える形にした部分こそが最も模倣しやすく、かつ Docker 自身が標準化のために手放した部分だからである。

収益構造：無償の技術の「周辺」から徴収する

収益の性質：シート単位のサブスクリプションによるストック型。課金単位が開発者数であるため、顧客企業のエンジニア採用がそのまま増収になる。逆に、コンテナの利用量がいくら増えても Docker, Inc. の収益は増えない。使用量ではなく人数に課金しているため、技術の普及と収益が連動しない構造になっている。

粗利の源泉：①Docker Engine が無償で世界中に配られているため、顧客獲得コストが低い。開発者は既に使っており、企業は使われている事実に対して後から支払う ②Docker Hub は公式イメージの供給元であり、置き換えには社内のビルドパイプライン全体の書き換えが要る ③製品の実体はデスクトップアプリと SaaS であり、変動費が薄い。

構造的な弱点：課金対象が中核技術そのものではなく、その周りの利便性と管理機能である。Docker Engine 相当の機能は Red Hat の Podman など無償の代替で置き換え可能であり、Docker Desktop を外して WSL2 や Colima で代替する回避策も広く知られている。中核が無償であるがゆえに、有償部分は常に払わずに済ませる方法と競合している。アナリストが Docker をプロダクトではなくフィーチャーだと評し、それが常に問題だったと述べるのは、この構造を指している26。

製品主導型成長（PLG）への転換：2019年以降の Docker は、企業のIT部門に営業する形から、開発者が無償で良い体験をし、組織として利用が拡大した段階で管理者が価値を認める機能に課金する形へ移行した。Scott Johnston はこの設計を明示的に語っている18。ネットドルリテンションは2020年末の1〜2カ月で80%から120%へ改善した21。

⑥転換点と示唆Inflection Points — なぜその判断が効いたか / 効かなかったか

転換点1（2013年）：捨てるはずだったものが本体になった

何が起きたか：本業の PaaS が伸び悩むなか、その裏側で使っていた内製のコンテナ管理ツールを OSS として公開したところ、本業を超える反響を得た1,2。会社は社名を Docker, Inc. へ変え3、翌年には旧本業を売却した4。

なぜ効いたか（Docker 固有の条件）：dotCloud が PaaS で戦っていた相手は Heroku であり、そこでの差別化要因はコンテナによる多言語対応だった。自社の競争優位そのものが、製品ではなく内部実装の側にあった。この状況では、優位の源泉を製品として切り出すことが最も合理的な打ち手になる。同じことは、内部実装に優位があるが製品では横並び、という条件が揃わない会社では成立しない。

実行上の条件：Hykes 本人が、これが6回目の試みであり、前の5回は本業と並行したから失敗したと述べている1。アイデアの正しさではなく、片手間をやめたことが変数だった。15人規模の組織で2本を同時に走らせられないという制約が、この判断の前提にある。

順序の設計：OSS 公開（2013年3月）→ 社名変更（同年10月）→ 旧本業の売却（2014年8月）と、反響を確認してから退路を断っている2,3,4。事後的に大胆な賭けと語られやすいが、実際の手順は逐次的である。

転換点2（〜2017年）：標準化を主導し、その過程で課金対象を手放した

何をしたか：Docker はコンテナランタイムの中核である libcontainer 一式を runc として Open Container Initiative へ寄贈した。仕様の草案とその参照実装の双方を提供しており、OCI ランタイム仕様 v1.0.0 は2017年7月19日に公開されている7。2017年3月29日には、コンテナ実行・イメージ転送・ローカルストレージを担う containerd を Cloud Native Computing Foundation へ寄贈した8。

なぜそうしたか：当時のコンテナ市場では CoreOS の rkt をはじめ複数の実装が乱立しかけており、標準が分裂すればエコシステム全体が育たない。Docker は自社実装を標準に据えることで分裂を防ぎ、事実上の勝者になった。技術的な目的は完全に達成されている。

何が代償になったか（ここが分岐点）：寄贈した containerd と runC は、Kubernetes が Docker Engine を介さずに直接呼び出す部品になった。Docker が標準化のために外へ出した部分は、そのまま Docker を経由せずにコンテナを動かすための部品になった。標準の主導権と、標準の実装からの徴収権は、この時点で切り離されている。

示唆：OSS で標準を取る戦略が誤りなのではない。誤りは、標準化の対象と課金対象の分離設計を後回しにした点にある。Docker が最終的に課金できたのは、寄贈しなかった Docker Desktop と Docker Hub、つまり標準の周辺にある利便性と配布経路だけだった。しかもその課金開始は2020年から2021年、containerd 寄贈から3、4年後である16,22。

転換点3（2016〜2017年）：Kubernetes にオーケストレーション層を取られた

何が起きたか：コンテナ単体が標準化された次の段階で、複数ホストにまたがるコンテナ群の配置・冗長化・自己修復を担うオーケストレーション層の主導権争いが起きた。Docker は Docker Swarm を、Google は Kubernetes を提示した。Kubernetes は2015年に CNCF へ移管され、ベンダー中立の旗のもとにクラウド各社が相乗りできる構造を得た。

決着の瞬間：2017年10月、コペンハーゲンで開かれた DockerCon EU で、Docker は自社の Docker Enterprise Edition と Docker for Mac / Windows に Kubernetes を統合すると発表した9。Swarm と Kubernetes を同じクラスタで動かせるようにするという建付けだったが、実質的には自社製オーケストレータの敗北宣言である。ここから2年後の Enterprise 事業売却まで、道筋は直線的につながる。

Swarm はなぜ負けたか（Docker 固有の条件）：

観点Docker SwarmKubernetes
設計思想簡単さを優先。Docker CLI の延長で使える宣言的モデル。望ましい状態を定義し、システムが収束させる
ガバナンス単一企業（Docker, Inc.）が所有2015年に CNCF へ移管され、ベンダー中立
大規模運用の実績限定的Google 社内の運用知見を出自として主張できた
クラウド事業者の動機競合企業の製品を自社サービスの中核に据える動機がない中立プロジェクトであるため、AWS・Azure・GCP が揃ってマネージドサービス化できた

核心：Swarm の敗因を使いにくかったで片づけるのは誤りで、むしろ Swarm のほうが簡単だった。決定的だったのは所有構造である。Kubernetes は CNCF に置かれたことで、Docker, Inc. の競合であるクラウド事業者全員が安心して採用・投資できる対象になった。Swarm は Docker, Inc. の資産であり続けたため、同じ相乗りが起きない。Docker はランタイム層では中立化を選んで標準を取り、オーケストレーション層では所有を選んで標準を失った。同じ会社が同じ時期に、真逆の判断を2つの層で行っている。

そして中立化した層からも徴収できなかった：ランタイム層を中立化した見返りは、標準の座であって収益ではなかった。2つの層で逆の判断をして、両方で収益化に失敗していることが、この会社の事業的苦境の根にある。

創業者本人は別の見立てを示している（併記しておく）：Hykes は当時、Docker のオーケストレータは20以上が同時に立ち上がっており、Kubernetes はそのうちの1つにすぎなかったと述べ、Docker にとって最大の実存的脅威は Kubernetes ではなく、商用製品を出せなかったことだったとしている11。この見立てを採れば、⑥の転換点2で述べた課金対象の設計の遅れこそが原因であり、Swarm の敗北はその結果にすぎない。本レポートは両者を排他的な説明とは見ず、所有構造の選択（Swarm）と課金対象の設計（Docker Hub / Desktop）の両方が同じ判断の癖から生じたと読む。いずれも、技術の普及を優先し、そこから徴収する経路の設計を後ろへ回している。

転換点4（2019年11月13日）：Enterprise 事業を売り、会社を作り直した

何が起きたか：同日に3つのことが発表された。①Mirantis による Docker Enterprise 事業の買収12,30 ②Docker, Inc. の資本再編と Benchmark・Insight Partners からの3,500万ドル調達13 ③Scott Johnston の CEO 就任13。

会社側の説明：Docker は経営陣と取締役会での分析の結果、社内に活発な開発者向け事業と成長中の企業向け事業という製品モデルも財務モデルも全く異なる2つの事業があると判断し、両者を分離したとしている13。

数字で見た実態：売却対象には約700社の企業顧客と約300名の従業員が含まれ、Fortune 100 の約3分の1が Docker Enterprise の利用企業だった12,14。売却後に残った Docker, Inc. は約60名18。売却前の全社ARRは7,500万ドル未満で、残った開発者向け事業のARRは2020年後半時点で約1,100万ドルにすぎない21。売ったのは別の事業ではなく、当時の売上の大半である。

買い手側の文脈：Mirantis は OpenStack を出自とするインフラ企業で、Kubernetes 事業への転換を進めていた。業界が Kubernetes へ移行するなかでの買収であり、Docker Enterprise の顧客基盤と Mirantis の Kubernetes 技術を組み合わせる形が取られた12,15。買われた側の技術ではなく顧客基盤が主目的だったという点が、この取引の性質を示している。

売却額：非開示12,30。報道は直近ラウンドの評価額を大きく下回るのは確実としているが、具体的な金額の推定は示していない14。本レポートも推定しない。

なぜこの判断が効いたと言えるのか：残った事業は2020年後半の約1,100万ドルから2022年1月に5,000万ドル超（前年度比4倍）、2022年末に約1.35億ドルへ伸びた18,21。ネットドルリテンションは80%から120%へ改善している21。Series C では21億ドルの評価額が付いた19,20。企業向け直販の重い組織を外し、開発者起点の製品主導型成長に一本化したことで、単位あたりの効率は明確に改善した。

同時に、何が効かなかったのか：この立て直しは、コンテナという技術が世界標準になった後に、その技術を作った会社が年商1億ドル台の開発者ツール企業として存続するという結果を意味する。技術の普及規模と会社の規模が桁で乖離した状態は、2019年の判断で解消されたのではなく、確定した。

転換点5（2020〜2021年）：無償で配ったものに、後から値段を付ける

何をしたか：2020年11月、Docker Hub に未認証100回／6時間、無償認証200回／6時間というイメージ取得のレート制限を導入した22,23。2021年8月31日には Docker Desktop のサブスクリプションを改定し、従業員250名超または年商1,000万ドル超の企業では有償契約を必須とした。既存の無償利用者には2022年1月31日までの移行猶予が置かれた16,17。

なぜ必要だったか：2019年に企業向け直販事業を手放した以上、収益源は開発者向け製品しか残っていない。しかし Docker Engine は無償の OSS であり、課金できる対象は Docker Desktop と Docker Hub に限られていた。選択肢は、無償で配ってきたものに値段を付ける以外に存在しなかった。

何が起きたか：レート制限は CI/CD パイプラインを直撃した。ビルドのたびにイメージを取得する構成では制限に容易に到達し、AWS や Red Hat が回避策の案内を出す事態になった22,23。Docker Desktop の有償化についても、無償利用を前提に業務プロセスを組んでいた企業から強い反発が出た17。

反発は継続している：2025年2月、Docker は予定していた取得回数の従量課金を全面撤回し、保管容量課金を無期延期した。将来課金を導入する場合は6カ月前に予告するとも表明している24。値付けの試みが、開発者側の反応によって押し戻された実例である。

Docker 固有の困難：一般に、無償から有償への移行が難しいのは心理的な抵抗のためだと説明される。だが Docker の場合、困難の本体はそこではない。Docker Hub は世界中の CI パイプラインに組み込まれた公共インフラのように扱われており、そこに制限をかけることは自社顧客ではない無数の第三者のビルドを壊す行為だった。課金対象の利用者と、影響を受ける利用者が一致していない。この非対称性は、OSS の中核を無償で配り、その配布経路だけを握るという構造を選んだ時点で決まっている。

転換点6（2025年〜）：AI 時代に配布基盤の座を取り直せるか

何をしているか：2025年4月、Docker は MCP Catalog と MCP Toolkit を発表した。Model Context Protocol サーバーの発見・認証・実行・管理を、コンテナの作法で扱えるようにするものである27。同時期に Docker Model Runner を投入し、ローカルホスト上で大規模言語モデルを実行する経路を用意した28。

賭けの内容：2013年に Docker が取った位置はアプリケーションの配布単位と配布経路だった。AI エージェントの時代に同じ役割を果たすのは、モデルとツール（MCP サーバー）の配布単位と配布経路になる。Docker Hub をそのまま MCP のカタログに転用できれば、2013年の勝ちパターンを再現できるという賭けである。

2013年と条件が違う点：①当時の Docker は無名の会社が空白地帯に置いたものだったが、今回は GitHub や各クラウド事業者が同じ場所を狙っている ②当時は課金設計を後回しにできたが、今回は既に収益化の難しさを経験済みで、無償で配って後から値付けする手は使いにくい ③MCP の仕様自体は Docker のものではないため、寄贈による標準化という2015年の手も使えない。

経営体制の含意：2025年2月に就任した Don Johnson は Oracle Cloud Infrastructure の創設者であり、その前は Amazon Web Services の初期からの技術リーダーである25。アナリストはこの人選を、ハイパースケーラーとの提携強化、そして最終的には売却の準備と読んでいる。船はこの5年で安定した、開発者ツールへの転換も済んだ、次は稼ぎに行く番だという評と、Docker はプロダクトではなくフィーチャーだ、それが常に問題だったという評が並記されている26。2,400万人の開発者基盤は、単体事業としてより買収資産として評価されているのが現在の外部評価である。

まとめ：この事例から取り出せるもの

転換点判断効いた／効かなかった理由（Docker 固有の条件）
2013 dotCloud → Docker本業の裏で使っていた内製ツールを OSS 公開し、反響を見てから本業を売却PaaS での競争優位が製品ではなく内部実装にあったため、優位の源泉を切り出すのが合理的だった。前5回が失敗したのは本業と並行したから
〜2017 標準化runc を OCI へ、containerd を CNCF へ寄贈標準分裂は防げた。ただし寄贈した部品が、Docker を経由せずコンテナを動かす部品になった。標準化対象と課金対象の分離設計が後回しだった
2016-17 Swarm 対 Kubernetes自社所有のまま Swarm で戦い、2017年10月に Kubernetes 統合を発表敗因は使いやすさではなく所有構造。CNCF 中立の Kubernetes にはクラウド事業者全員が相乗りできたが、競合企業所有の Swarm には誰も乗れない
2019 Enterprise 事業売却売上の大半（約700顧客・約300名）を Mirantis へ売り、60名で再出発単位効率は改善し ARR は伸びた。ただしそれは、標準を作った会社が年商1億ドル台のツール企業として存続するという結果の確定でもある
2020-21 有償化Docker Hub のレート制限と Docker Desktop の企業有償化2019年に企業向け事業を手放した以上、他に収益源がなかった。だが Docker Hub は第三者のCIに組み込まれた公共インフラ化しており、課金対象と影響範囲が一致しない。2025年に一部撤回24
2025- AI 配布基盤MCP Catalog / Toolkit と Model Runner で AI 時代の配布経路を狙う2013年の勝ちパターンの再現を狙うが、空白地帯ではなく、寄贈による標準化も使えず、無償先行の値付けも使いにくい。外部評価は売却準備と読んでいる26
この事例が示す論点：Docker の経緯は OSS では稼げないという話ではない。Red Hat も MongoDB も、OSS を出発点にして事業を成立させている。Docker に固有だったのは、課金できる位置を確保する前に、標準を取るために課金しうる部分を先に手放したという順序である。runc と containerd を寄贈し終えた2017年の時点で、Docker には Docker Hub のレート制限も Docker Desktop の有償プランも存在しなかった。値付けの設計を始めたのは2020年、寄贈から3年後で、その時には既に Docker Hub が世界中の CI に組み込まれた後だった。標準化と収益化のどちらを先にやるかではなく、両者の対象を分けて同時に設計していたかが分岐点である。技術が業界標準になったこと自体は、Docker にとって最大の成果であり、同時に最大の制約になった。
